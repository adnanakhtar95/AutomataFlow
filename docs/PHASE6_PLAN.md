# Phase 6 — Customer management dashboard

**Status:** authorized 2026-11-20 (Phases 6–10 authorization, docs/DECISIONS.md). **Complete (2026-11-20)**; acceptance criteria 1–9 met (evidence below).

## Objective
A customer-facing React dashboard over the real Api: an operator signs in, configures and publishes a workflow, uploads
records, runs a job, monitors it, investigates failures (attempts, logs, screenshots, artifacts) and exports results,
without engineering help. Every number and list comes from the Api; nothing is mocked in the product.

## Scope
- Stack (ADR-076): React 19, TypeScript, Vite, Tailwind CSS 4, TanStack Query, openapi-fetch, react-router, types
  generated by openapi-typescript from a committed OpenAPI snapshot guarded by a contract test.
- Authentication with session restoration (ADR-077): HttpOnly refresh cookie, access token in memory only, cross-tab
  serialized refresh, route protection, unauthorized/forbidden states.
- Shell: sidebar, header, workspace identity, user menu, breadcrumbs, responsive layout, error boundaries.
- Overview with real statistics (new aggregate endpoint).
- Workflows: list with search, detail, version history, guided form editor driven by the action catalog the Api exposes
  (only the 13 implemented actions), JSON editor, server-side validation without saving, draft save, publication with
  attestation acknowledgement, archive.
- Imports and jobs: CSV/JSON upload with client-side pre-checks (extension, size) and server validation summary, invalid
  records, job list, detail, progress, cancel, requeue (NeedsReview), results export.
- Execution: records by status, attempts, logs, screenshots (authorized blob download), artifacts, failure details,
  reconciliation and NeedsReview visibility.
- Workspace: secrets (names, write-only values) for Admins. Membership management is Phase 8 (no backend yet).
- Platform-operator functions are not exposed in the customer dashboard.

Not in scope: drag-and-drop designer, billing, member management (Phase 8), production images (Phase 7, except what the
end-to-end harness needs).

## Acceptance criteria
1. Log in; reload keeps the session; logout revokes it.
2. Dashboard statistics come from the Api.
3. Select a workflow, edit a draft with the form editor, validate, publish.
4. Upload a CSV, create a job, see the validation summary and invalid records.
5. Monitor execution until completion (polling).
6. Investigate a failed record: attempts, logs, screenshot.
7. Export results CSV.
8. Viewer cannot see write actions; Operator cannot publish; another workspace's ids give "not found".
9. Verified by an automated browser journey against the real Api, Worker, PostgreSQL and DemoCrm.

- 2026-11-20, full container verification at the step-1–4 working tree (before the e2e harness): UnitTests 1264/1264,
  DemoCrm.Tests 157/157, IntegrationTests 112/112, AutomationTests 242/243. The one failure,
  `SupervisedRecoveryTests.P6`, stopped 2 min 41 s after its second Worker started although its deadline is 6 min (the
  whole test ran 3 min 11 s): the container's wall clock (`DateTime.UtcNow`) jumped forward, which happens in Docker
  Desktop's VM under load (images were being pulled in parallel). The Worker log shows the correct sequence
  (InFlight, then AwaitingFence). Re-run alone: passed (3 min 23 s). No Phase 6 change touches the Worker, journal or
  supervisor. Recorded as an environment-timing incident, not a pass of the original run.
- Dashboard (host, Node 24): lint clean, `tsc --noEmit` clean, 34/34 Vitest tests, production build, API types match
  the snapshot. The container stage of the verification script runs the same checks.
- 2026-11-20, first end-to-end run (`scripts/e2e-dashboard.ps1`, release images): the journey passed in 2.6 min. The
  database afterwards: job `CompletedWithErrors`, records 7 Succeeded / 6 Failed / 1 Invalid, 7 confirmation
  screenshots, no fence needed. The Worker log showed one `Heartbeat failed ObjectDisposedException`: an attempt that
  finished between the heartbeat's snapshot and its cancellation. Fixed with `RunningAttempts` (registration before
  the work starts, cancellation of a finished attempt is a no-op, disposal only when no cancellation is in progress;
  5 tests incl. 500 instant attempts and concurrent cancel/finish).
- Full run b: UnitTests 1264, DemoCrm.Tests 157, IntegrationTests 112 all passed; AutomationTests 247/248. Failure:
  `SupervisionTests.P7_P11f` could not start its unit: "setpriv: setresgid failed: Invalid argument" and
  "tee: /proc/N/gid_map: No such file". **A real launcher race** (pre-existing since ADR-075): the unit wrapper waited
  for its uid map only, so `setpriv --regid=1000` could run before the launcher wrote the gid map; the wrapper died and
  the container failed to start (Docker's restart policy recovered it in production). Fixed: the wrapper waits for both
  maps (`deploy/worker/af-worker-launch.sh`), pinned by `LauncherScriptTests`.
- Full run c: all passed except AutomationTests 249/250: `Cancelling_a_job_stops_further_records_without_extra_submissions`
  found the in-flight record `NeedsReview` (`CancelledWithOpenAmbiguity`) where it asserted `Cancelled`. The
  cancellation reached the attempt after its side effect started; NeedsReview is the specified outcome (ADR-072). The
  test's assumption was timing-dependent (it passed in runs a and b); it now asserts the real invariants: at most the one
  in-flight record interrupted, only with that code, and no submission for any record that never started.
- **Full run d (final tree): all green.** UnitTests 1264/1264, DemoCrm.Tests 157/157, IntegrationTests 112/112,
  AutomationTests 250/250 (real Chromium with sandbox, real Worker processes, supervision container with the production

## Security review (step 6)
| Area | Control | Evidence |
|---|---|---|
| Refresh token theft by script | HttpOnly, Secure, SameSite=Strict cookie scoped to `/api/v1/auth`; body token `null` for browsers; no web storage (lint rule) | `BrowserSessionTests` (integration), `session.test.ts`, e2e asserts cookie flags and empty storage |
| CSRF on cookie endpoints | the cookie is honoured only with `X-AutomataFlow-Session: browser`; no CORS; SameSite=Strict | integration test: cookie without header gives 400 |
| Refresh-token reuse across tabs | single-flight per tab plus a Web Lock across tabs; sign-out broadcast | `session.test.ts` |
| XSS | API text rendered as text only (`dangerouslySetInnerHTML` forbidden by lint); gateway CSP `script-src 'self'`, no inline script, `object-src 'none'`, `base-uri 'none'` | lint; e2e asserts zero CSP violations in the console |
| Clickjacking | `frame-ancestors 'none'`, `X-Frame-Options: DENY` | gateway configuration |
| Token in URLs / referrers | bearer header only; artifacts and exports as blob object URLs; `Referrer-Policy: no-referrer` | `client.test.ts`, component test of the export, e2e screenshot `src` is `blob:` |
| Artifact content sniffing | the Api serves `application/octet-stream` + `nosniff`; the dashboard re-types only PNG/JPEG for display | `download.ts`, existing artifact tests |
| Tenant isolation | every new read endpoint takes the organization from `ICurrentUser`; cross-tenant tests on hosts with and without the query-filter backstop; the UI shows "not found" for foreign ids | `DashboardReadsWithBackstop`/`WithoutBackstop`, e2e step 10 |
| Privilege display | navigation and actions hidden by role; the Api enforces every policy (Viewer cannot validate, Operator cannot publish/requeue) | component tests, `WorkflowAuthoringApiTests` |
| Platform-operator functions | not exposed in the dashboard | route table |
| Rate limiting behind the gateway | `X-Forwarded-For` honoured only from `Proxy:TrustedNetworks` | configuration; see residual risk |
| Secrets | write-only values; the value field is a password field and is cleared after submit; never logged | component test, e2e |
| Swagger / health exposure | the gateway returns 404 for `/swagger*` and `/health*`; Swagger is served only in Development | gateway configuration |
| Upload limits | client pre-check (extension, size, empty) for early feedback; the Api remains authoritative | `lib.test.ts`, existing upload tests |

Residual risks (carried to Phase 7):
- `Proxy:TrustedNetworks` must match the deployment network; a wrong value either loses per-client rate limiting or
  trusts spoofed addresses. The deployment validation of Phase 7 checks it is set when the gateway is used.
- TLS is not terminated by the gateway image; production requires a TLS terminator in front (Phase 7 deployment guide).
  Over plain HTTP on a non-localhost name, browsers drop the Secure cookie and sessions cannot be restored after a reload.
- The JSON tab is a plain text area; very large definitions are bounded by the Api's definition limits only.
